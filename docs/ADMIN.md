# API de administração do servidor

Contrato entre o `lumi-server` e um futuro painel de administração. Espelha os comandos do terminal (`lumi-server token|user|session|vault|federation|mirror|audit|status`): mesmas regras, mesmas recusas. Inspirado no ADR 0037 do porvia; as diferenças estão no fim.

## Transporte
- Listener próprio em `LUMI_ADMIN_ADDR` (ex.: `0.0.0.0:8081` na rede interna do compose, sem porta publicada). Vazio: desligado. Não confundir com `LUMI_ADMIN_USERNAME`/`LUMI_ADMIN_PASSWORD`, que só criam o primeiro usuário.
- Recusa subir (código de saída 78) se colidir com a API pública (`LUMI_BIND_ADDR:LUMI_PORT`), comparando endereços resolvidos: mesma porta e hosts que se sobrepõem (`0.0.0.0`/`::` cobrem tudo; `localhost`, `127.0.0.1`, `::1` e `::ffff:127.0.0.1` são o mesmo loopback; um nome de host não resolvido na mesma porta também é recusado). A porta é aberta na partida: se estiver ocupada, o servidor não sobe.
- Fora do loopback, avisa no log: o lumi não termina TLS, então o token trafega em claro; use só numa rede privada.
- IP do cliente: `X-Forwarded-For` só vale quando o par TCP está em `LUMI_ADMIN_TRUSTED_PROXIES` (lista de CIDRs ou IPs; no compose, `172.16.0.0/12`). O cabeçalho é lido da direita para a esquerda e vale o primeiro salto que não é proxy confiável. O painel deve enviar o IP de quem o usa: vai para a auditoria e para o limite de falhas.
- Mesmos timeouts da API pública (leitura 30 s, escrita 60 s, ociosidade 120 s) e os mesmos cabeçalhos de segurança, mais `Cache-Control: no-store`. Corpo limitado a 16 KiB (`413`). Sem CORS: quem chama é o servidor do painel, nunca o navegador.
- Base `/admin/v1`. Toda rota exige `Authorization: Bearer lpa_…` (token) ou `Bearer lps_…` (sessão de admin), exceto `POST /admin/v1/session`, que faz o login por senha. Rotas desconhecidas sob `/admin/v1` respondem `404` só depois da autenticação.
- `GET /admin/healthz` responde `200 {"status":"ok"}` sem token, para o healthcheck do contêiner.
- Datas em RFC 3339 UTC (como o resto da API do lumi); `null` quando não há.
- Corpo JSON estrito: `Content-Type: application/json`, campos desconhecidos e dados depois do objeto são recusados com `400`.

## Tokens
- `lpa_` + 32 bytes aleatórios em base64url (47 caracteres); o banco guarda só o SHA-256 (`admin_tokens.token_hash`).
- Criados só no terminal: `lumi-server token create <nome> [--ttl 30d]` imprime o token uma única vez, sozinho no stdout (`TOKEN=$(lumi-server token create painel)`). `token list` e `token revoke <id>` completam. A API lista e revoga, mas nunca cria: um token vazado não se perpetua.
- Nome: 1 a 64 caracteres, sem caracteres de controle. Validade padrão de 30 dias, mínima de 1 minuto e máxima de 1 ano (`--ttl` aceita `720h`, `90m` ou `30d`).
- `last_used_at` é gravado no máximo uma vez por minuto.
- Token ausente, malformado, desconhecido, expirado ou revogado (ou um token de sessão de usuário da API pública): sempre `401 {"error":"unauthorized"}` com `WWW-Authenticate: Bearer realm="lumi-admin"`. Só as falhas gastam e consultam o limite por IP (10 de rajada, uma a mais a cada 6 s; IPv6 agrupado por /64); acima dele, as falhas recebem `429 {"error":"rate_limited","retry_after_s":N}` com `Retry-After`. Um token válido passa sempre, mesmo desse IP.

## Login com conta de usuário (sessões `lps_`)
- Administradores do servidor são usuários comuns com a marca `server_admin` (migração 0009). Quem dá ou tira a marca: o terminal (`lumi-server admin grant|revoke <user>`), a API (`POST /users/{id}/server-admin`) ou a partida inicial. O admin criado por `LUMI_ADMIN_USERNAME`/`LUMI_ADMIN_PASSWORD` num banco vazio já nasce com a marca. Num servidor antigo (antes da 0009) sem nenhum administrador marcado, a partida dá a marca a `LUMI_ADMIN_USERNAME` só se a conta existir, estiver ativa e a senha dela ainda for `LUMI_ADMIN_PASSWORD`; se não, use `lumi-server admin grant <user>`. A migração em si nunca marca ninguém.
- `POST /admin/v1/session` com `{"username", "password"}` (sem token). Passa pelas mesmas regras do login público: bcrypt (com hash falso para usuário inexistente, mesmo custo), limites em memória por IP e por usuário compartilhados com `POST /api/auth/login`, e o bloqueio persistente (`failed_logins`/`locked_until`): senha errada conta, sucesso zera. Por cima, vale o limite de falhas por IP do listener de admin (o mesmo dos tokens): sem saldo, a tentativa é recusada com `429` antes de conferir a senha.
- Exige `server_admin`. Usuário inexistente, senha errada, conta bloqueada ou desativada e conta sem a marca recebem a mesma resposta, `401 {"error":"invalid_credentials"}`; limite estourado, `429 {"error":"rate_limited","retry_after_s":N}` com `Retry-After`. Toda recusa grava `admin.login_failed` na auditoria (`reason`, nome de usuário mascarado, `user_id` quando a conta existe, IP e user agent). Senha certa de quem não é admin não conta para o bloqueio.
- Sucesso: `201 {"token": "lps_…", "id", "name": "session", "kind": "session", "expires_at", "user": {"id", "username"}}`. `lps_` + 32 bytes aleatórios em base64url (47 caracteres), guardado só como SHA-256 em `admin_tokens` (`kind = 'session'`, `user_id`). Vale 12 h, sem renovação (o banco recusa mais que isso). Auditoria `admin.session.create` com o usuário em `user_id`.
- A sessão vale em todas as rotas, como um token. Deixa de valer na hora se o usuário perde a marca, é desativado, troca a senha (pela API pública ou pelo admin), tem as sessões encerradas (`DELETE /users/{id}/sessions`) ou é apagado (as sessões dele somem junto, por `ON DELETE CASCADE`).
- `DELETE /admin/v1/session` encerra a sessão da própria chamada (`204`, auditoria `admin.session.logout`); com um token `lpa_` responde `409` (token se revoga por id). As sessões aparecem em `GET /tokens` com `kind: "session"` e o usuário, e `DELETE /tokens/{id}` também as revoga.
- Sessões expiradas ou revogadas há mais de 30 dias são apagadas quando outra sessão é criada.
- Nas ações feitas com uma sessão, a auditoria leva `token_id` = id da sessão e `token_name` = `"session"`; quem era o usuário se descobre pela sessão (que some no apagamento LGPD dele).

## Rotas
Todas sob `/admin/v1`.

| `GET /users/{id}` | — | um usuário, com `"owned_vault_ids": [...]` |
| `POST /users` | `{"username", "password", "display_name"?}` | `201` usuário |

| `GET /tokens` | — | página de tokens e sessões de admin por criação |

### Formatos
- Estado (`GET /status`): além das contagens, `db_latency_ms` (ida e volta de uma consulta trivial ao banco, em ms com fração), `users_disabled`, `users_locked` (bloqueados e não desativados), `crdt_bytes` (soma de todos os cofres), `logins_24h` e `login_failures_24h` (linhas `auth.login` e `auth.login_failed` da auditoria nas últimas 24 h), `invites_active` (convites não revogados, não expirados e com usos sobrando) e `go_version`.
- Usuário: `{"id", "username", "display_name", "state", "disabled_at", "failed_logins", "locked_until", "sessions", "owned_vaults", "vaults", "created_at", "last_login_at", "last_seen_at", "server_admin"}`. `state` é `"active"`, `"disabled"` ou `"locked"` (desativado vence). `sessions` conta as não expiradas; `vaults` conta participações (inclui as que possui). `last_login_at` é a linha `auth.login` mais recente da auditoria; `last_seen_at`, o último uso de uma sessão ainda guardada; `null` quando não há.
- Sessão: `{"id", "user_id", "username", "created_at", "last_used_at", "expires_at"}`. `id` é o SHA-256 (hex, 64 caracteres) do token guardado no banco: identifica a sessão, mas não serve para autenticar.
- Cofre: `{"id", "slug", "name", "owner": {"id", "username"}, "members", "federated_members", "notes", "crdt_bytes", "federation": {"role": "home"|"follower", "active_links"} | null, "created_at"}`. `crdt_bytes` soma snapshots e atualizações Yjs guardados (não o tamanho em disco). Também `"head_seq"` (última sequência de mudança do cofre neste servidor, `0` sem nenhuma), `"last_change_at"` (`null` sem nenhuma) e `"invites_active"`.
- Membro: `{"user": {"id", "username"}, "display_name", "role": {"id", "name"}, "owner", "joined_at"}`. Papel: `{"id", "name", "seed", "members"}`.
- Convite: `{"id", "vault": {"id", "slug", "name"}, "inviter": {"id", "username"}, "role": {"id", "name"}, "email_hint", "max_uses", "use_count", "state", "expires_at", "created_at", "revoked_at"}`. `id` é o SHA-256 (hex, 64 caracteres) do token: identifica o convite, mas não serve para entrar; o token nunca sai pela API de admin. `state` é `revoked`, `expired`, `exhausted` ou `active`, nessa ordem de precedência. `inviter.username` vem vazio se a conta já foi apagada.
- Federação: `{"id", "vault": {"id", "slug", "name"}, "role", "peer_url", "jurisdiction", "status", "last_acked_seq", "control_seq", "created_at", "revoked_at", "mode", "sever_policy", "head_seq", "mirror_acked_seq", "home_seq", "lag_seq", "pending_deletes", "oldest_pending_delete_at", "last_contact_at", "paused_at", "promoted_at", "violations_24h", "backfill"}`. `role` é o papel **deste** servidor; `control_seq` só no lado `home`; `status` é `active`, `revoked` ou `severed`. `mode` é `replica` (bidirecional) ou `mirror` (cópia somente leitura, docs/SPEC-ESPELHO-SELADO.md parte A); `sever_policy` é `keep` ou `purge` (o que o espelho faz com a cópia quando a origem revoga). No lado `home` de um espelho: `head_seq` é a sequência atual do cofre aqui, `mirror_acked_seq` a última que o espelho confirmou ter aplicado, `lag_seq` a diferença, `pending_deletes` quantas exclusões (lápides) o espelho ainda não confirmou e `oldest_pending_delete_at` a mais antiga delas — é a medida de quanto a exclusão/apagamento LGPD ainda não chegou ao espelho. No lado espelho: `home_seq` é a sequência da origem já aplicada, `promoted_at` marca um espelho promovido e `backfill` é `{"active", "synced", "total"}` (só com o servidor no ar e o vínculo conectado; `null` no terminal). `violations_24h` conta as tentativas do espelho de mandar conteúdo nas últimas 24 h (`federation.mirror_violation`). `paused_at` não nulo: vínculo pausado.
- Token: `{"id", "name", "state", "created_at", "last_used_at", "expires_at", "revoked_at", "current", "kind", "user"}`; `state` é `active`, `expired` ou `revoked`; `current` marca o token da chamada; `kind` é `token` (`lpa_`) ou `session` (`lps_`); `user` é `{"id", "username"}` numa sessão e `null` num token. Em `GET /status`, `token` é `{"id", "name", "expires_at", "kind", "user"}`.
- Auditoria: `{"id", "created_at", "action", "user_id", "vault_id", "ip", "user_agent", "payload"}`. É o `audit_log` inteiro (ações dos usuários também); `scope=admin` filtra as `admin.*`.
- Filtros da auditoria: `action` é uma ação exata (`auth.login`) ou um prefixo terminado em `.*` (`auth.*`), até 64 caracteres de `[a-z_.]`; `since` e `until` em RFC 3339 (`created_at >= since` e `< until`; `until` precisa ser depois de `since`).
- Busca (`q`): de 1 a 64 caracteres, sem caracteres de controle; vazio é o mesmo que ausente; `%` e `_` valem literalmente.
- Páginas: `{"items": [...], "more", "next"}`. `?limit=` de 1 a 200 (padrão 200) e `?after={next}` para a seguinte; `next` é opaco e `null` na última.
- Ids inválidos no caminho respondem `404`, como ids desconhecidos.

### Regras
- Usuário e senha seguem as regras do cadastro: nome com 3 a 32 de `[a-z0-9_-]`, em minúsculas, sem separador nas pontas; senha com 8 a 72 bytes, não só dígitos, e só letras exige 10. `display_name` até 80 caracteres. Nenhum consentimento é registrado em nome do usuário.
- Bloqueio: depois de 10 senhas erradas seguidas numa conta existente, o login é recusado por 2^(n−10) s, até 15 min. Conta desativada ou bloqueada recebe no login a mesma resposta de senha errada (`401 invalid_credentials`), e toda sessão de conta desativada deixa de valer.
- Apagamento (`DELETE /users/{id}`): o mesmo fluxo do `DELETE /api/users/me`. Quem é dono de cofres é recusado com `409 {"error":"sole_admin_vaults","vault_ids":[...]}`, sem nada apagado nem auditado, a menos que `delete_owned_vaults=true` (os cofres e diretórios vão junto). Cofres em que só é membro continuam sem ele; as linhas de auditoria dele são anonimizadas (`user_id`, `ip`, `user_agent` nulos; `username` vira `<redacted>`); as sessões e streams do feed são encerrados; os servidores seguidores recebem o novo estado de controle.
- Erros no formato da API pública, `{"error": código, "detail"?}`: `400 validation_failed` (com `"field"` e `"detail"`), `401 unauthorized`, `404 not_found`, `409 conflict` (ex.: nome de usuário em uso, federação já revogada; `detail` diz o motivo), `409 sole_admin_vaults`, `413 payload_too_large`, `429 rate_limited`, `500 internal`.

## Auditoria
- Toda ação que muda algo grava uma linha em `audit_log` e uma entrada no log do servidor (`component=admin`) com o token usado (id e nome, nunca o valor), o alvo e o IP.
- `action`: `admin.token.create` (só no terminal), `admin.token.revoke`, `admin.user.create`, `admin.user.password`, `admin.user.disable`, `admin.user.enable`, `admin.user.unlock`, `admin.user.delete`, `admin.user.logout`, `admin.user.server_admin` (`payload.enabled`), `admin.session.revoke` (sessão de usuário da API pública), `admin.session.create` e `admin.session.logout` (sessão de admin `lps_`), `admin.login_failed` (login por senha recusado), `admin.invite.revoke`, `admin.vault.delete`, `admin.federation.revoke`, `admin.federation.pause`, `admin.federation.resume`, `admin.mirror.resync` e `mirror.promote` (só no terminal; `payload` com `federation_id`, `peer_url`, papéis criados e atualizados e as contagens de membros levados, sem conta local e de outros servidores).
- Eventos de espelho gravados pelo próprio servidor, sem ator de admin: `federation.mirror_violation` (na origem: o espelho mandou conteúdo e o vínculo foi fechado; `payload.peer_url`, `frame`, `note_id`; três em uma hora revogam o vínculo), `federation.peer_denied` (na origem: uma réplica mandou uma escrita que o estado de controle não permite aos usuários dela; `payload.frame`, `reason`), `mirror.local_write_blocked` (no espelho: uma escrita local foi recusada) e `mirror.purged` (no espelho: cópia apagada ao ser revogada com `sever_policy: purge`).
- `payload`: `{"actor": "admin", "token_id", "token_name", ...alvo}`; nunca senha nem token (`admin.invite.revoke` guarda só os 12 primeiros caracteres do id do convite e o `vault_slug`; `admin.user.logout`, o `username` e o número de sessões encerradas). Ações do terminal têm `token_id` nulo e `token_name` `"cli"`. `ip` é o do cliente do painel (nulo no terminal).
- Quando o alvo é um usuário, a linha leva o id dele em `user_id` e o nome em `payload.username`: o apagamento LGPD dele anonimiza também essas linhas (inclusive o IP do admin nelas).
- Mudanças feitas só pelo serviço de administração (senha, desativar, ativar, desbloquear, encerrar sessão, encerrar todas as sessões, revogar convite, tokens e sessões de admin, marca `server_admin`, criar usuário) gravam a auditoria na mesma transação: se a linha não puder ser escrita, nada muda. Apagar usuário, apagar cofre e revogar federação passam pelos serviços de domínio: a linha é gravada antes e, se falhar, a ação não acontece; se a ação falhar depois, o log do servidor registra a falha. Esses serviços gravam ainda os seus próprios eventos (`user.delete`, `vault.delete`, `federation.revoke`).

## Terminal
`lumi-server help` lista os comandos. `lumi-server admin list [--json]` lista os administradores do servidor; `admin grant <user>` e `admin revoke <user>` dão e tiram a marca (com a mesma recusa do último administrador). `token list` mostra também as sessões de admin (colunas `KIND` e `USER`), e `token revoke <id>` também as encerra. `<user>` aceita nome ou id; `<vault>`, slug ou id. As listas aceitam `--json` (mesmos formatos da API, sem paginação). Senhas: `--password-stdin` lê uma linha do stdin; sem ele, pede duas vezes no terminal, sem eco. `user delete` e `vault delete` pedem para digitar o nome do alvo, ou `--yes` quando o stdin não é um terminal. O terminal só precisa do banco e de `LUMI_ROOT` (as mesmas variáveis do servidor); com o servidor rodando, o efeito no banco é imediato, mas streams do feed abertas fecham na próxima checagem (até 1 min), WebSockets de notas ficam até reconectar e um vínculo de federação já aberto continua até reconectar ou reiniciar — por isso, com o servidor no ar, prefira a API. A exceção são pausa, retomada, ressincronização e promoção de vínculos: o servidor no ar confere as linhas de federação a cada 15 s e aplica o que o terminal mudou.

### Espelhos (`lumi-server mirror …`)
Um espelho é uma cópia somente leitura de um livro cuja origem é outro servidor (docs/SPEC-ESPELHO-SELADO.md parte A). A origem cria o convite com `POST /api/vaults/{id}/federation-invites {"mode": "mirror", "sever_policy"?: "keep"|"purge"}` (capacidade `vault.federate`); um operador do servidor espelho entra com `POST /api/federation/join {"home_url", "token", "mode": "mirror"}`. No espelho, todo papel vira no máximo `note.read` + `vault.export`: toda escrita responde `403 {"error":"mirror_read_only"}`, nada de fswatch nem de semeadura do CRDT, e `GET /api/vaults` mostra `"mirror": true` e `federation.role: "mirror"`. Quem lê o espelho são os membros que a origem concede como `usuario@url-do-espelho`.
- `mirror list [--vault v] [--json]`: os vínculos de espelho (dos dois lados), com a defasagem (`LAG`: na origem, sequências atrás e exclusões pendentes; no espelho, a sequência da origem aplicada). `federation list --mode mirror|replica` filtra do mesmo jeito.
- `mirror status <id> [--json]` (também `federation status`): detalhe de um vínculo.
- `mirror pause|resume <id>` (também `federation pause|resume`): para ou retoma o vínculo sem revogar.
- `mirror resync <id>`: só no espelho; esquece o progresso e refaz a passada completa.
- `mirror promote <vault> --confirm`: só no terminal (a API de admin não tem a rota: um token de admin sozinho não pode bifurcar um livro). Numa transação, corta o vínculo com a origem, marca o espelho como promovido (a trava de somente leitura sai, fswatch e semeadura voltam), transforma os papéis do último estado de controle da origem em papéis locais e os membros `usuario@este-servidor` que existem aqui em membros locais (o dono continua Admin). Lista quem não foi levado (contas de outros servidores e contas inexistentes aqui). Não há volta automática: religar à origem antiga é uma federação nova. Depois de promover, reinicie o servidor para que ele largue o vínculo antigo na hora (senão, até 30 s).
- Revogação pela origem: com `sever_policy: keep` (padrão) o espelho guarda uma cópia congelada, ainda somente leitura; com `purge` ele apaga o cofre (`mirror.purged`). O cumprimento disso depende da honestidade do operador do espelho, como qualquer cópia.

## Diferenças em relação ao porvia (ADR 0037)
- Erros em `{"error", "detail"}` como no resto do lumi, em vez de `application/problem+json`; datas em RFC 3339, não milissegundos.
- Auditoria no `audit_log` existente (com filtro `scope=admin`), não numa tabela à parte, para o apagamento LGPD alcançar também as linhas de admin.
- Ids do lumi são UUIDv4: páginas por `username`, `slug` ou `(criação, id)`, com cursor opaco.
- Sessões não têm id próprio: o id é o hash do token.
- Sem TLS no processo: o aviso fora do loopback vale sempre.
- O bloqueio por falhas de login passou a ser persistente (migração 0007), para o painel poder mostrá-lo e desbloquear; os limites em memória da API pública continuam.
